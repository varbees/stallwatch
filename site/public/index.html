Your machine froze.
Every monitor says it’s fine.

Linux has measured how long tasks spend blocked since 4.20, and it writes that number into every cgroup on the system. Almost nothing reads it. stallwatch does, and names the systemd unit — then the process inside it — that stopped your machine.

what it tells you

why utilisation lies

cpu  some avg10=1.6the CPU is idle
io   full avg10=51.3everything is frozen half the time

A CPU graph reports a healthy machine here. In fact, for 51% of those ten seconds, every non-idle task on the system was blocked.

That second number is Pressure Stall Information. some means at least one task was blocked; full means every non-idle task was blocked at once. The kernel writes cpu.pressure, memory.pressure and io.pressure into every cgroup — so the data needed to name a culprit has been sitting there since 2018.

htop, node_exporter and KDE’s system monitor all read the system-wide /proc/pressure/* files and stop. You learn that the machine stalled, never who stalled it. That gap is the whole tool.

it blames the cause, not the victim

Two things make naming a culprit harder than reading a number, and stallwatch learned both by getting them wrong first.

Kernel accounting is hierarchical. A stall inside firefox.scope also counts against app.slice, user@1000.service, user.slice and the root. Report that naively and the answer is always user.slice, which helps nobody. stallwatch walks the tree and blames a cgroup only when no single child owns ≥80% of its stall.

PSI blames the victim. It measures who is blocked. A dd saturating the disk sits in a sibling cgroup showing a fraction of the pressure of the terminal it is starving — so drilling into the worst cgroup finds the casualty and misses the culprit. High bytes with low blocking is causing the stall; high blocking with low bytes is suffering it. Both are reported, labelled.

four ways to ask

  • stallwatch

    One-second snapshot. --processes names the process, --json for machines, --watch to follow.

  • stallwatchd  ·  --since 30

    A freeze is over by the time you can open a terminal and type. The daemon records into a bounded ring so you can ask afterwards. Peaks are kept, never averaged away — a 2s freeze inside a 60s window averages to 3% and disappears.

  • Varlink  ·  dev.stallwatch.Monitor

    Queryable with systemd’s own varlinkctl, no bespoke client. Chosen over D-Bus specifically because speaking D-Bus means either a dependency or hand-rolled SASL, and both were worse.

  • Prometheus  ·  /metrics

    Names aligned with the container_pressure_* vocabulary cAdvisor and Kubernetes already settled on. Validated against the official prometheus_client parser, not just against its own tests.

what it refuses to do

A diagnostic that guesses is worse than no diagnostic, because you act on it. These are constraints in the code, not intentions.

  • It will not claim causation from correlation

    A drive here read 97 °C. stallwatch says nothing about it — that sensor publishes no threshold of its own, and the drive’s throttle counters were zero across 4,979 power-on hours. It had never once throttled. A temperature without a threshold is not evidence, so it is never reported as one.

  • It will not ask for root

    Everything is read from /proc and /sys as you. A diagnostic that needs privileges is a diagnostic people don’t run.

  • It will not fix anything

    Strictly read-only. It has no tuning knobs, drops no caches, kills no processes. It tells you what stopped; what to do about it is yours.

  • It will not grow a dependency tree

    Zero crates, std only — so the engine stays reducible to a C ABI and a C or C++ project could adopt it without a Rust toolchain entering their build.

specifics

0 dependencies 516 KB static binary 81 tests 0.9% of one core, resident 3.0 MB RSS

Needs a kernel with CONFIG_PSI=y, which is near-universal. If your distribution builds with CONFIG_PSI_DEFAULT_DISABLED=y — openSUSE historically did — add psi=1 to the kernel command line. Runs unprivileged in a container if you mount the host cgroup tree read-only; note that /proc/pressure is not namespaced, so a container reading it sees the host’s numbers as if they were its own.
